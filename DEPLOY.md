# Deploying StuffSearch

Goal: the app runs on a real phone with **no Metro / Expo dev server** and **no paid
Apple or Google developer account**. Both builds embed the JS bundle, so once
installed they are fully standalone and work offline from the dev machine.

---

## Android — release APK

Prerequisites (already satisfied on the Windows dev box): JDK 17, Android SDK
with platform 36 + build-tools 36, and `ANDROID_HOME` set.

**`JAVA_HOME` must point at JDK 17, not a newer one.** The box also has JDK 21
installed and `JAVA_HOME` has drifted to it; building that way fails in a
third-party module with

```
Execution failed for task ':jamsch-expo-speech-recognition:compileReleaseKotlin'.
> Inconsistent JVM-target compatibility detected for tasks
  'compileReleaseJavaWithJavac' (17) and 'compileReleaseKotlin' (21).
```

Expo pins Java to 17 while Kotlin follows the JDK, so the two disagree. Check
with `java -version`, and override for one build rather than changing the
machine:

```powershell
$env:JAVA_HOME = "C:\Program Files\Microsoft\jdk-17.0.20.8-hotspot"
```

### Build

```powershell
cd android
.\gradlew.bat assembleRelease
```

Output: `android/app/build/outputs/apk/release/app-release.apk` (~115 MB, ~8 min
from clean).

The APK is universal (armeabi-v7a, arm64-v8a, x86, x86_64), so it installs on any
phone or emulator. That is most of the 115 MB — for a modern phone only, this
cuts it to roughly a third and builds much faster:

```powershell
.\gradlew.bat assembleRelease -PreactNativeArchitectures=arm64-v8a
```

### Install

```powershell
# USB: enable Developer options -> USB debugging, accept the phone's prompt.
.\scripts\install-android.ps1

# Wi-Fi, first time (Developer options -> Wireless debugging -> Pair with code):
.\scripts\install-android.ps1 -PairAddress 192.168.1.50:37123 -PairingCode 123456 -WifiAddress 192.168.1.50:5555

# Wi-Fi, already paired:
.\scripts\install-android.ps1 -WifiAddress 192.168.1.50:5555
```

Or just copy `app-release.apk` to the phone (Drive, USB storage, Syncthing…) and
tap it — Android will ask you to allow installs from that source.

If the install fails with `INSTALL_FAILED_UPDATE_INCOMPATIBLE`, an older build
signed with a different key is on the phone. Remove it first:
`adb uninstall com.stuffsearch.app`.

### Signing

Release APKs are signed with `stuffsearch-release.keystore` (repo root),
credentials in `keystore.properties`. **Both are gitignored — back them up
somewhere safe.** If you lose them you can still sideload, but you'll have to
uninstall the old app first (losing its local data) because the signature won't
match. The cert is valid until 2054.

`android/` is regenerated by `expo prebuild`, so the signing wiring lives in
`plugins/withAndroidReleaseSigning.js` rather than in `android/app/build.gradle`.
Without `keystore.properties` present, the build falls back to the debug keystore
so a fresh clone still builds.

## iOS

**The hard constraint:** Apple only lets a free Apple ID sign an app for **7
days**. After that the app refuses to launch until it is re-signed. There is no
way around this without the $99/yr Apple Developer Program — it is enforced by
the provisioning profile, not by the build. Building an `.ipa` at all also
requires macOS.

So there are two options, and only one of them is expiry-free:

| | Where it runs | Signing | Expires |
|---|---|---|---|
| **Simulator build** | iOS Simulator on a Mac | none needed | **never** |
| **Device build** | your physical iPhone | free Apple ID | every 7 days |

### Getting the code onto the Mac

There is no git remote configured. Either push one, or copy the folder across
excluding `node_modules/`, `android/`, and `ios/`. **`.env` is gitignored but
required** — copy it manually; the `EXPO_PUBLIC_SUPABASE_*` values are baked into
the build and the app is inert without them.

### Build

On the Mac, with Xcode installed from the App Store:

```bash
# Never-expiring Release build in the Simulator:
./scripts/mac-ios-build.sh sim

# Release build onto a USB-connected iPhone (prompts you through free-Apple-ID
# signing in Xcode the first time, then expires after 7 days):
./scripts/mac-ios-build.sh device
```

To renew an expired device install, re-run `./scripts/mac-ios-build.sh device`.
It reinstalls over the top and keeps the app's local data.

### Alternative: build the simulator app on EAS instead of locally

If you'd rather not install Xcode's full toolchain, `eas.json` has a `simulator`
profile that builds a standalone (non-dev-client) Simulator app on Expo's macOS
infrastructure. It needs a free Expo account, no Apple account:

```bash
npx eas-cli build --profile simulator --platform ios
```

Download the resulting archive on the Mac, unzip it, and drag the `.app` onto a
running Simulator. Same as above: no signing, no expiry.

## After changing code

Nothing hot-reloads in these builds — the bundle is baked in. Rebuild and
reinstall:

- Android: `cd android && .\gradlew.bat assembleRelease` then
  `.\scripts\install-android.ps1`
- iOS: `./scripts/mac-ios-build.sh sim` (or `device`)

Bump `version` in `package.json` when you want the phone to show a new version
number; `versionCode` lives in `android/app/build.gradle` and is regenerated by
prebuild, so raise `version` rather than editing it directly.

## Troubleshooting: stuck on the splash spinner

Symptom: the app shows a spinning `ActivityIndicator` forever and never reaches
the sign-in or home screen. `adb logcat -s ReactNativeJS:V` shows only
`Running "main"` and no error.

Why it's silent: these are **release** builds. Hermes does not forward JS
exceptions to logcat and `console.*` is a no-op outside `__DEV__`, so a thrown
promise or a never-resolving `await` produces no log output. The spinner is one
of two startup gates in `app/_layout.tsx` (`RootLayout` waits on `initI18n`,
`Gate` waits on `useAuth().loading`) — if either gate's async work rejects or
stalls, the spinner never clears.

Two defenses are built in:

1. **On-screen error overlay.** Both gates are wrapped in try/catch and render
   an `InitErrorView` with the actual error message instead of spinning forever.
   If you see a red "Startup error" line, that message is the cause — no
   logcat needed. (This is how release-only init failures are diagnosed.)
2. **Auth gate no longer blocks on the network.** `useAuth().loading` is cleared
   as soon as `supabase.auth.getSession()` (a local SecureStore read) resolves.
   The profile fetch (`loadProfile`, a network query) runs in the background and
   cannot stall the gate. Previously `setLoading(false)` sat behind
   `await loadProfile`, so a slow/stalled profiles query — a network blip, a
   Supabase cold start, or a token refresh in flight — hung the app
   indefinitely. The sequencing lives in `src/lib/authBootstrap.ts` and is
   pinned by `src/lib/__tests__/authBootstrap.test.ts`.

If the spinner returns, first confirm the phone can reach Supabase
(`adb shell ping <project>.supabase.co`), then relaunch
(`adb shell am force-stop com.stuffsearch.app && adb shell am start -n
com.stuffsearch.app/.MainActivity`) and read the overlay if one appears.
