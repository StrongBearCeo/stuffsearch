# StuffSearch — Full Implementation Plan (v3, with sharing + external barcode binding)

A cross-platform (iOS, iPadOS, Android phone + tablet) household inventory app. Scan app-generated QR codes **or any externally-printed barcode** to assign items to places, search by name/voice/description, and ask an LLM "where did I put the...?". **Multi-user:** families/roommates share a household; a user can belong to several households and switch between them. Bilingual (English + Vietnamese) from day one.

## Confirmed decisions
- **Framework:** React Native + Expo (free; full native access; targets Samsung S26, iPhone, iPad, Samsung Tab)
- **Backend:** Supabase (Postgres + Auth + Storage + pgvector)
- **Barcodes:** App auto-generates QR codes for items & places; AND users can scan *any* existing externally-printed code (any symbology) and bind it as an item's/place's identifier
- **External code rules:** any symbology binds as identifier; on conflict, resolve across ALL the user's households (offer to switch); unique per household; app-printed codes always auto-generated (no custom content)
- **LLM scope:** semantic "describe it" search, voice transcription, item enrichment, NL location queries
- **Voice:** On-device STT, pluggable to cloud later
- **Languages:** English + Vietnamese (i18n from day one)
- **Sharing:** Household-scoped; invite via link/QR + email/magic-link; Owner + Member roles; one user can join multiple households and switch
- **Scope:** Full implementation in one pass

## Tech stack
- **App:** Expo SDK 51+, expo-router (file-based nav), TypeScript, React Native Reanimated, NativeWind (Tailwind), React Query (cache) + Zustand (UI/session state)
- **Camera/Scan:** `expo-camera` + `expo-barcode-scanner` (reads QR, Code128/39/93, EAN-13/8, UPC-A/E, Codabar, ITF, DataMatrix, PDF417, Aztec); QR generation via `react-native-qrcode-svg`
- **Voice:** on-device `@jamsch/expo-speech-recognition` (iOS SFSpeechRecognizer + Android SpeechRecognizer), solid en-US/vi-VN
- **i18n:** `i18next` + `react-i18next`, `expo-localization`
- **Backend:** Supabase JS client, Postgres + **pgvector**, Auth (email magic-link + password), Edge Functions for LLM
- **LLM:** OpenAI default (gpt-4o-mini chat/vision, text-embedding-3-small embeddings); key in Supabase secrets, never in the app
- **Printing QR:** `expo-print` + `expo-sharing` (AirPrint + share to PDF)

## Sharing model
- A **household** is the sharing scope. All items and places belong to a household, not a user. Every member sees everything in the household.
- **Roles:** Owner (creates household, invites/removes members, can delete household or any item/place, controls settings) and Member (add/edit/move items & places, scan-to-assign, invite if Owner allows). Members cannot remove others or delete the household.
- **Joining:** Owner taps "Invite" → app generates invite link + QR (`stuffsearch://invite/<token>`). Supabase Auth handles sign-up (email magic-link or password). First launch: create a household OR scan an invite code to join one.
- **Multi-household:** a user can be a member of several; an on-screen switcher (avatar menu) swaps active scope. Each membership records role + joined_at.
- **Audit:** every item move and every create/edit records `actor_id` ("who moved it / who added it").

## External barcode binding model (new in v3)
- An item or place is identifiable by EITHER an app-generated token (in `qr_token`, unguessable, deep-linkable) OR one or more externally-supplied codes — or both.
- **`external_codes` table** — `id`, `household_id`, `code_value` (text, the raw decoded payload), `code_type` (enum of symbology: qr, code128, ean13, upc_a, datamatrix, pdf417, aztec, etc.), `entity_type` (item|place), `entity_id`, `label` (optional, e.g. "shelf label"), `bound_by`, `bound_at`. UNIQUE `(household_id, code_value)` — a given external code binds to at most one item/place within a household. Indexed on `code_value` for fast scan lookup.
- **Scan resolution state machine** (`src/lib/scanner.ts → resolveScan(payload)`):
  1. If payload matches a StuffSearch deep-link (`stuffsearch://item/<token>`, `…/place/<token>`, `…/invite/<token>`) → route accordingly (invite handled by join flow; item/place opened directly, scoped to whichever household owns it, with a switch prompt if it's not the active one).
  2. Else treat payload as a raw external code → query `external_codes` across **all households the user belongs to**:
     - **No match in active household, match elsewhere** → prompt "This code belongs to '<name>' in the '<Household>' household. Switch and open?" → on confirm, switch active household and open/assign.
     - **Match in active household** → open that item/place (or, if a place is the current "active place" and this was an item scan, assign the item to the place and log history with `moved_by`).
     - **No match anywhere** → offer to **create a new item or place** pre-filled with the scanned code bound as its identifier (and optionally trigger LLM enrichment if the code looks like a product barcode — see below).
- **Code-type-aware enrichment (built in, not a separate user choice):** during the "create from external code" flow, if `code_type` is EAN/UPC, the app offers to look the code up (Open Food Facts / UPCitemdb) to auto-fill name/image/category — exactly the product-barcode enrichment use case — while still binding the scanned code as the identifier. QR/Code128/etc. just bind as a custom identifier.
- **Printing:** app-printed codes remain auto-generated random tokens only (per your decision). External codes are never re-printed by the app.

## Database schema (Supabase / Postgres + pgvector)
- **profiles** — `id (uuid = auth.users)`, `display_name`, `avatar_url`, `default_language`, `voice_provider`, `created_at`
- **households** — `id`, `name`, `photo_url`, `owner_id`, `invite_token` (unique, rotatable), `created_at`
- **household_members** — `household_id`, `user_id`, `role enum('owner','member')`, `joined_at`, PK(household_id, user_id)
- **places** — `id`, `household_id`, `name`, `description`, `photo_url`, `parent_place_id`, `qr_token` (app-generated, nullable if identified only by external code), `created_by`, `created_at`
- **items** — `id`, `household_id`, `name`, `description`, `category`, `photo_urls[]`, `product_link`, `qr_token` (app-generated, nullable), `current_place_id`, `current_place_since`, `embedding vector(1536)`, `metadata jsonb`, `created_by`, `last_moved_by`, `created_at`, `updated_at`
- **external_codes** — `id`, `household_id`, `code_value` (text), `code_type` (enum), `entity_type` (item|place), `entity_id` (uuid), `label`, `bound_by`, `bound_at`; UNIQUE(household_id, code_value); index on code_value. (Replaces reliance on a single `barcode` column — one entity may carry multiple external codes.)
- **item_history** — `id`, `item_id`, `place_id`, `moved_by`, `moved_at`, `note`
- Embeddings refreshed via trigger/Edge Function on item insert/update.

**RLS (household-scoped):** every row carries `household_id`; policies allow read/write iff the requesting user is a member of that household. Owner-only operations (delete household, remove member, transfer ownership) enforced via `household_members.role`. `external_codes` lookup uses a SECURITY DEFINER function `resolve_code(code_value, user_id)` that scans all households the user belongs to and returns `(household_id, entity_type, entity_id)` or null — safe cross-household resolution.

**Scan-to-assign flow:** scanning an item code sets its `current_place_id` to the app's current "active place" and writes an `item_history` row with `moved_by = current user`. Scanning a place code sets it active and lists its contents.

## QR / external code scheme
- **App codes:** `stuffsearch://<type>/<qr_token>?h=<household_short_id>`; deep-linked via Expo universal links. Auto-generated random tokens only.
- **External codes:** any symbology; raw decoded payload stored in `external_codes.code_value`. Resolution handled by `resolveScan()` (above), not deep-linking.
- **Print screen:** paginated PDF of all unprinted app-generated item + place codes (labels for items, larger tags for places), AirPrint or share to PDF. Does not reprint external codes.

## LLM features (Supabase Edge Functions, key in secrets)
1. **`enrich-item`** — barcode + photo → suggested name/category/description/product_link (vision model); user confirms before saving.
2. **`product-lookup`** — EAN/UPC external code → product DB (Open Food Facts / UPCitemdb) → name/image/category; used by the "create from external code" flow.
3. **`semantic-search`** — embed query (`text-embedding-3-small`), pgvector cosine match within active household, ranked results. Multilingual → EN + VI.
4. **`ask-llm`** — NL question → retrieves relevant items+places within active household → chat model answers with the specific location; app renders answer + tap-through to place + room photo.

## Voice
- `speech.ts` wraps `@jamsch/expo-speech-recognition`: start/stop, partial results, locale (en-US / vi-VN). `VoiceButton` reused on search and item notes. Pluggable so Whisper can be added later.

## i18n
- `react-i18next` with `en.json` / `vi.json` under `src/locales/`. Device locale auto-detected; user can override in Settings. UI strings, voice prompts, and LLM system prompts all localized.

## Responsive (phone + tablet)
- NativeWind breakpoints; tabs collapse to a sidebar on iPad/Tab; lists use a 2-column grid on tablet; scan overlay scales to both.

## Implementation milestones (one full codebase, sequenced for reviewability)
1. **Scaffold:** Expo project, expo-router, NativeWind, i18n, Supabase client, theme, env. README setup.
2. **Auth + households:** magic-link/password auth, HouseholdProvider, create/join household, invite link/QR, member list, roles, household switcher, active-household context.
3. **Schema + migrations:** full SQL with pgvector + external_codes + household-scoped RLS + resolve_code function + seed.
4. **Core CRUD:** items/places list, detail (with history + bound codes), add/edit (incl. "create from scanned external code"), image upload to Storage.
5. **Code binding + product lookup:** external_codes CRUD, `resolveScan()` state machine, product-lookup Edge Function for EAN/UPC.
6. **QR system (app codes):** generation, print screen, deep-link handling for item/place/invite.
7. **Scanner:** camera scan tab wired to `resolveScan()` — scan-to-assign, scan-to-review, cross-household resolve + switch prompt, "active place" state, `moved_by` tracking.
8. **Search:** text + catalog browse + filters (household-scoped).
9. **Voice:** STT integration + VoiceButton on search.
10. **LLM:** enrich-item + semantic-search + ask-llm Edge Functions and app wiring.
11. **Polish:** offline cache + conflict handling, tablet layouts, settings, EN/VI review pass.

## What you'll need to provide
- Supabase project URL + anon/service keys (free tier is fine)
- An LLM provider API key (OpenAI recommended; stored in Supabase secrets, not the app)
- Apple Developer account only when shipping to the App Store (not needed to run on your own devices via Expo Go or ad-hoc builds)

## Out of scope for this first build (explicit)
- Per-item / per-place privacy within a household (schema is household-wide)
- Push notifications / reminders ("item not seen in a year")
- Web admin dashboard (can reuse the same Supabase backend + i18n later)
- Importing from an existing inventory spreadsheet (can be added as an Edge Function)
- Re-printing or regenerating external codes inside the app (external codes are read-only bindings)
